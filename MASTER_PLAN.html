북극성현재 기준선단계안전 게이트품질운영의사결정

1. 북극성과 비목표

가장 중요한 규칙: 사람의 명시적 승인 없이 실전 주문, 모의 주문, 자동매매 시작, 비상정지 해제, credential 변경, DB 파괴 작업을 실행하지 않는다. 개발 harness는 외부 주문을 제출하지 않는다.

북극성

  • 모든 주문은 올바른 broker/profile/account scope에서 실행된다.
  • 불확실한 상태는 주문 허용이 아니라 차단으로 귀결된다.
  • 재시작이 손실 한도·비상정지·pending 상태를 우회하지 않는다.
  • 운영자가 주문 전후 상태와 provider trace를 설명할 수 있다.

비목표

  • 백테스트 성과만으로 전략을 실전 배포하지 않는다.
  • 프론트엔드를 credential 또는 주문 상태의 권위자로 만들지 않는다.
  • provider API를 공통 OrderManager 밖에서 빠르게 우회하지 않는다.
  • 문서 수를 늘리기 위해 기존 상세 문서를 복제하지 않는다.

2. 현재 구현 기준선

React Page / Feature → TanStack Query hook → command wrapper → shared transport (Tauri IPC | Web REST) → Rust command/server facade → AppState → BrokerScope + strategy/manual request → provider preflight → RiskManager + TradeGuard → OrderManager reservation → KIS/Toss → pending/order → fill → trade/stats/risk persistence

Frontend

TanStack Router, Query, Zustand, MUI. API 계약은 src/api와 src/shared/api, route UI는 FSD 계층에 있다.

Backend

commands/*와 server/*가 facade, broker/*가 provider 경계, trading/*가 전략·주문·리스크 도메인이다.

Durability

JSON/DB 공통 storage 경계가 pending, order, trade, stats, strategy, risk를 저장한다. backend 장애는 조용히 fallback하지 않는다.

3. 단계별 실행 계획

0

변경 전 기준선 고정

작업 트리·branch·remote를 기록하고 사용자 변경을 분리한다. 관련 코드, 테스트, IPC/구조 문서를 읽어 실제 흐름을 확인한다.

Exit: 범위, 비목표, 위험 등급, rollback과 검증표가 작성됨.

1

계약과 scope 명시

Rust serde↔TS 타입, Tauri↔Web 노출, BrokerScope, query cache, persisted schema의 변경 여부를 표로 만든다.

Exit: 누락 없는 호출자·저장 소비자 목록.

2

가장 좁은 경계에서 구현

도메인 로직은 command/UI에 복제하지 않는다. provider 호출 전 검증, 짧은 lock, submission 예약, fail-closed persistence 정책을 보존한다.

Exit: focused test와 타입/check 통과.

3

회귀와 실패 경로

정상 경로보다 scope mismatch, 잔고 부족, 통화 불일치, 동시 주문, timeout, 저장 실패, restart 복원을 먼저 검증한다.

Exit: 전체 Rust lib test 및 관련 frontend/E2E 통과.

4

운영 준비

관측 필드, provider trace, 비상정지와 rollback 절차, data migration을 검토한다. 민감 값은 결과/로그에서 제거한다.

Exit: 운영 체크리스트와 잔여 위험 승인.

5

점진적 활성화

별도 승인 후 정지 상태 배포 → 설정 확인 → read-only → 모의/소액 수동 검증 → 제한된 자동매매 순으로 확장한다.

Stop: scope/pending/persistence/risk health가 불명확하면 다음 단계 금지.

5. 품질 전략과 도구

항상 가까운 harness

npx tsc --noEmit
npm run check:fsd
cargo check --workspace --all-targets --locked
cargo test --workspace --lib --locked

변경 범위별 focused test, Playwright, project map, provider spec은 HARNESS_MAP.md를 따른다.

탐색 도구 정책

Serena: 공용 타입·IPC·주문·리스크 변경에서 다중 모듈 참조 누락 위험이 있을 때 선택 사용한다.

Graphify: 모듈 이동, 공용 helper 추출, 호출 계층 재편 같은 구조 리팩터링 때만 사용한다. 일반 기능·문서 변경의 의무 단계가 아니다.

테스트의 주장 한계

preview는 candle-close replay와 비용·리스크 가정을 제공하지만 live cadence, intrabar, provider latency, 실제 체결을 완전히 재현하지 않는다. mock Playwright는 실제 Tauri/provider E2E가 아니다. 이 한계를 완료 보고와 운영 승인에 명시한다.

6. 운영·장애 대응

배포 전

  • 자동매매 정지
  • pending 주문 대조
  • 데이터/DB export·rollback 확인
  • scope와 risk runtime 확인
  • 민감 파일 비포함 확인

관측

  • trading health
  • broker rate limit
  • buy/persistence suspension
  • provider order/request/TR trace
  • risk loss/emergency state

즉시 중단

  • scope 불일치
  • 중복 주문
  • pending 저장 실패
  • 체결 대조 불가
  • risk 복원 실패
  • credential 노출 의심
주문 이상 시 우선순위
신규 주문 차단 또는 자동매매 정지 → provider의 open order/체결 상태를 읽기 전용으로 확인 → local pending/order/trade/risk ledger와 대조 → 로그와 최소 trace 보존 → 원인과 scope가 확정되기 전 자동 해제 금지.
저장 장애 시 원칙
provider 접수 후 local 저장 실패는 주문 미발생으로 간주하지 않는다. provider order id를 보존하고 모든 신규 주문을 차단한 뒤 reconciliation한다. DB 장애를 JSON으로 몰래 fallback하여 두 권위 원천을 만들지 않는다.
credential 사고 시 원칙
로그/이슈/문서에 값을 재인용하지 않는다. 자동매매를 정지하고 토큰·키를 provider에서 폐기/회전하며, Git history와 artifact 노출 범위를 별도 보안 절차로 확인한다.

7. 의사결정·완료 정의

작업 완료

  • 요구사항과 비목표가 충족됐다.
  • 변경된 계약·문서가 동기화됐다.
  • focused 및 범위 전체 harness 결과가 기록됐다.
  • 실거래/모의주문 미실행 여부가 명확하다.
  • 기존 사용자 변경이 보존됐다.
  • 잔여 위험과 rollback이 보고됐다.

운영 활성화 승인

  • 코드 완료와 별개의 결정이다.
  • 운영자가 계좌·scope·한도·시장 상태를 확인한다.
  • read-only와 모의/소액 검증 결과를 검토한다.
  • 비상정지·reconciliation 담당자가 준비됐다.
  • 정해진 손실/오류 임계치에서 자동 중단한다.
